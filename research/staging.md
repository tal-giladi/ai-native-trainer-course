### C-20261007-01 · Claude Code sandbox-escape CVE history (TOCTOU/symlink pattern), latest Oct 5 2026

- **Class:** A
- **Kind:** correction
- **Date discovered:** 2026-10-07
- **Date published:** 2026-10-05
- **Source:** https://github.com/anthropics/claude-code/security/advisories/GHSA-5j29-h97v-84ch
- **Organization/researchers:** Anthropic (publisher of the advisory); vulnerability reported by researcher "c_h4ck_0" via HackerOne
- **Category:** agent-security
- **What changed:** GitHub Security Advisory GHSA-5j29-h97v-84ch (CVE-2026-103435), published 2026-10-05, discloses a Time-of-Check-to-Time-of-Use (TOCTOU) race condition in Claude Code: a target file path is validated against the project working directory at permission-check time, then re-resolved **without re-validation** at write time; an attacker able to write into the shared workspace can swap a project file for a symlink between the two steps, so Claude Code's unsandboxed write follows the symlink and writes to an arbitrary file **outside the sandboxed workspace**. CVSS v4.0 7.7 (High); CWE-22 (path traversal), CWE-61 (symlink following), CWE-367 (TOCTOU). Affected `@anthropic-ai/claude-code` npm package < 2.1.129; fixed in 2.1.129. This is the latest of a recurring pattern of disclosed Claude Code sandbox-escape/bypass advisories through 2026, all on the project's own GitHub Security Advisories page (github.com/anthropics/claude-code/security/advisories): GHSA-7835-87q9-rgvv "Sandbox Escape via Git Worktree Path Confusion" (2026-06-25, High), CVE-2026-39861 "Sandbox Escape via Symlink Following" (CVSS 8.8, High — same symlink-following mechanism as the Oct 5 advisory, different code path), CVE-2026-25725 "Sandbox Escape via Persistent Configuration Injection in settings.json" (High), plus unrelated host-level issues GHSA-5p5x-5294-qhp3, GHSA-3rwf-2g6p-c2f9, GHSA-5cwg-9f6j-9jvx. Independent secondary coverage (e.g. a security newsletter's "week of sandbox escapes" roundup) frames this as a cross-vendor pattern also seen in OpenAI Codex, Cursor and Gemini CLI, not unique to Claude Code — noted here as context, not relied on as a source for any claim.
- **Technical summary:** The sandbox's filesystem confinement is enforced by path validation that happens once (at permission-check time) rather than being re-checked atomically at the moment of the write syscall. Any TOCTOU gap of this shape lets a symlink substitution redirect a benign, already-approved write to a sensitive host path (the GHSA text gives shell configuration files as the example impact). The fix (2.1.129) re-validates at write time; the underlying bug class (trust a path once, use it later) is exactly the kind of thing worth naming explicitly rather than only gesturing at "a determined attacker."
- **Why it might matter:** Lesson 09.5 teaches the sandbox as the actual enforcement boundary — "a Bash rule matches the command text... For enforcement that does not depend on the command text you need the sandbox" and "the sandbox is the boundary" — with the Limitations section only generically noting "a determined adaptive attacker may still find a path." This gives a dated, CVSS-scored, vendor-patched, primary-sourced incident in the exact product and mechanism the lesson teaches, and shows it is a recurring vulnerability *class* (TOCTOU/symlink races), not a one-off curiosity — good concrete material for "what it does NOT guarantee" / "how an attacker adapts" and for the "keep auto-update on" mitigation already implicit in the lesson's design.
- **Evidence of adoption:** n/a (vulnerability disclosure, not a product feature)
- **Major organizations using it:** n/a
- **Open-source implementation:** none
- **Paper:** none
- **Code:** none
- **Relationship to existing course material:** lessons/module-09/lesson-05.md (09.5 — sandbox-is-the-boundary claim and Limitations section); references/research-log.md row "Claude Code docs — Sandboxing" (accessed 2026-09-28, `implementation` volatility, due for re-verification)
- **Potential course lesson:** FIX 09.5 — add one dated real-world example to the Limitations section citing this recurring TOCTOU/symlink sandbox-escape pattern (GHSA-5j29-h97v-84ch / CVE-2026-103435, patched 2.1.129; GHSA-7835-87q9-rgvv) as evidence for "a determined adaptive attacker may still find a path," paired with "keep Claude Code on auto-update" as the concrete mitigation. Strengthens rather than contradicts the lesson's core claim.

### C-20261008-01 · Black Hat 2026: zero-privilege GitHub issue reaches CI runner secrets in Claude Code and Gemini CLI (two CVEs, both patched)

- **Class:** A
- **Kind:** new-topic
- **Date discovered:** 2026-10-08
- **Date published:** 2026-06-13 (Claude Code GHSA), 2026-06-24 (Gemini CLI CVE per mirrors), presented at Black Hat USA 2026 on 2026-08-05
- **Source:** https://github.com/anthropics/claude-code/security/advisories/GHSA-fg94-h982-f3mm (fetched directly, primary); Gemini CLI advisory GHSA-wpqr-6v78-jr5g / CVE-2026-12537 (could not fetch the GitHub or GitLab mirror directly — both domains are blocked by this session's egress proxy — so that half is corroborated only via secondary trackers: https://cybersecuritynews.com/critical-gemini-cli-vulnerability/amp/, https://vpncentral.com/critical-gemini-cli-vulnerability-lets-attackers-execute-code-in-ci-cd-workflows/, https://feedly.com/cve/CVE-2026-12537); Black Hat talk (secondary coverage only — i.blackhat.com is also blocked for this session): https://labs.cloudsecurityalliance.org/research/csa-research-note-ai-coding-agent-cicd-secrets-20260808-csa/, https://dailysecurityreview.com/resources/claude-code-and-gemini-cli-flaws-expose-ci-workflow-secrets/
- **Organization/researchers:** Elad Meged, Novee Security (Black Hat USA 2026 talk "Trusted Enough to Run"); GHSA-fg94-h982-f3mm credits "hackerone.com/novee"; advisories published by Anthropic (GHSA CNA) and Google
- **Category:** agent-security
- **What changed:** Two confirmed, vendor-patched CVEs show that an attacker with **zero repository privileges** — just the ability to open a GitHub issue or PR — can reach CI runner secrets once a coding agent processes that content in a headless/CI job. (1) **CVE-2026-54316 / GHSA-fg94-h982-f3mm (Claude Code, npm `@anthropic-ai/claude-code` >=0.2.54 <2.1.163, fixed 2.1.163, CVSS v4 base 6.0 Moderate, CWE-183/200/515):** the bare hostname `huggingface.co` was pre-approved for WebFetch, so *any* path on that domain — including attacker-controlled model repos — was auto-approved with no permission prompt and no `--allowedTools` restriction. Untrusted content that reaches Claude's context (e.g. issue text in a CI job) can direct WebFetch at a repo path like `/resolve/main/config.json`; HuggingFace counts the request as a "download" server-side, giving a covert channel to exfiltrate whatever Claude can read (files, env vars, command output) one encoded request at a time. (2) **CVE-2026-12537 / GHSA-wpqr-6v78-jr5g (Gemini CLI <0.39.1 and `run-gemini-cli` GitHub Action <0.1.22, fixed 0.39.1/0.1.22; CVSS reported inconsistently across mirrors as either 7.8 or a CVSS-3.1 10.0 "critical" — I could not load the GHSA page itself to resolve this):** in headless/CI mode the launcher read `.gemini/.env` from an untrusted workspace and passed values into an OS command without neutralizing shell metacharacters, before the sandbox even started — i.e. OS command injection from a file an attacker's PR can carry. The fix stops loading workspace config unless the folder is explicitly trusted, and is flagged as a breaking change for existing non-interactive CI workflows. Secondary sources also describe a similar, less-detailed class of finding against OpenAI Codex, but I could not confirm a CVE or technical detail for it from any source I could reach — treat that third leg as unconfirmed.
- **Technical summary:** Both bugs are instances of the course's own "trust boundary" framing (lesson 09.1): a CI job that feeds issue/PR text (untrusted content) to an agent that also holds CI secrets (private data) and can reach the network (external comms) satisfies the lethal-trifecta/Rule-of-Two test the moment it runs. Claude Code's bug is specifically a *sink* the course's trust model would flag — an "approved" domain treated as fully trusted when only the domain, not every path on it, should have been. Gemini CLI's bug is a *headless-mode* trust failure — config auto-loaded from an untrusted workspace before any sandbox or allowlist applied.
- **Why it might matter:** Lesson 07.6 already tells students "Run the eval job only for branches of your own repository... keep `permissions: contents: read`" and explicitly says "Module 9 goes further" on this exact risk; lesson 09.1 teaches the lethal-trifecta/Rule-of-Two test and that "a ticket in your own Jira is untrusted"; lesson 09.6 tells students not to run agent-driven evals on untrusted PRs. This gives two dated, CVE-numbered, vendor-patched, primary-sourced (for the Claude Code half) real incidents in the *exact* failure mode (headless agent + CI secrets + attacker-controlled issue/PR text) those lessons already warn about — strong concrete material, not a contradiction of anything currently taught.
- **Evidence of adoption:** n/a (vulnerability disclosure)
- **Major organizations using it:** n/a
- **Open-source implementation:** none
- **Paper:** none (conference talk; slides at i.blackhat.com, which this session could not reach)
- **Code:** none
- **Relationship to existing course material:** lessons/module-07/lesson-06.md (07.6 — "Module 9 goes further" on this exact CI-secrets risk); lessons/module-09/lesson-01.md, lesson-04.md (OWASP LLM06 Excessive Agency), lesson-06.md (09.6 — "do not run agent-driven evals on untrusted pull requests"); references/research-log.md rows for Claude Code headless docs (07.5/07.6) and OWASP LLM06 (09.4), both due for re-verification
- **Potential course lesson:** ADD a short real-world case-study callout to 09.1 or 09.6 (and/or 07.6) citing CVE-2026-54316 and CVE-2026-12537 as concrete instances of "zero-privilege issue/PR text + CI secrets + headless agent = exfiltration," alongside the existing abstract trifecta framing. Not a FIX (nothing currently taught is wrong), purely additive evidence.

### C-20261008-02 · METR discloses $600K API-key theft where an attacker prompted an agent to reveal its own provider key

- **Class:** B
- **Kind:** new-topic
- **Date discovered:** 2026-10-08
- **Date published:** 2026-08-31 (METR's own post); incident occurred March 2026; wide secondary pickup 2026-09-24/25
- **Source:** https://metr.org/blog/2026-08-31-security-update/ (primary — **could not be fetched**; metr.org is blocked by this session's egress proxy, same restriction noted for platform.claude.com in yesterday's run). Corroborating secondary coverage, cross-checked across multiple independent outlets: https://www.theregister.com/a/5293730, https://www.infosecurity-magazine.com/news/attackers-steal-metr-api-key/, https://thehackernews.com/2026/09/attackers-steal-metr-api-key-and.html, https://www.itpro.com/security/cyber-attacks/hackers-ran-up-a-usd600-000-ai-bill-after-swiping-api-keys-says-metr-and-nobody-realized-for-weeks
- **Organization/researchers:** METR (self-disclosed)
- **Category:** agent-security
- **What changed:** METR (the AI-evaluation nonprofit the course already cites for productivity-experiment methodology, 07.4/07.5/10.4) disclosed that in March 2026 a researcher ran agents on a personal, internet-facing EC2 instance meant to sit behind Google auth; a "fail-open" bug in that app silently disabled authentication for several days. The instance held an API key for METR's general-access models account. Per secondary reporting, the attacker found the exposed instance, **prompted the agent directly to reveal the model-provider API key it held**, added a persistent SSH key, and used the stolen credential for about three weeks, consuming roughly $600,000 of (donated, so unbilled) model credits before anyone noticed — no billing alert fired because the credits were free and usage blended into METR's normal high-volume eval traffic. METR says no sensitive data was accessed and has since restricted putting credentials/data on non-METR infrastructure and added spend alerts.
- **Technical summary:** This is not a coding-agent product vulnerability (unlike C-20261008-01) — it is a cloud-misconfiguration (fail-open auth) plus a prompt-extraction of a secret the agent had direct access to in its own environment, i.e. a real-world instance of "don't put raw provider credentials in an agent's env if the agent can be asked to reveal them."
- **Why it might matter:** Matches lesson 09.4's OWASP LLM06 Excessive Agency framing (minimize what an agent can access; a secret in reach is a secret that can be exfiltrated) and the general "agent acts with the union of every tool/credential it can reach" framing in 09.1. Useful as a second, independently-sourced real-world case study if the weekly review wants one beyond the CI/CD-specific CVEs above — it is about operational practice (secrets in an agent's environment) rather than a specific product bug.
