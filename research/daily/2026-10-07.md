### C-20261007-01 · Claude Code sandbox-escape CVE history (TOCTOU/symlink pattern), latest Oct 5 2026

- **Class:** A
- **Kind:** correction
- **Date discovered:** 2026-10-07
- **Date published:** 2026-10-05
- **Source:** https://github.com/anthropics/claude-code/security/advisories/GHSA-5j29-h97v-84ch
- **Organization/researchers:** Anthropic (publisher of the advisory); vulnerability reported by researcher "c_h4ck_0" via HackerOne
- **Category:** agent-security
- **What changed:** GitHub Security Advisory GHSA-5j29-h97v-84ch (CVE-2026-103435), published 2026-10-05, discloses a Time-of-Check-to-Time-of-Use (TOCTOU) race condition in Claude Code: a target file path is validated against the project working directory at permission-check time, then re-resolved **without re-validation** at write time; an attacker able to write into the shared workspace can swap a project file for a symlink between the two steps, so Claude Code's unsandboxed write follows the symlink and writes to an arbitrary file **outside the sandboxed workspace**. CVSS v4.0 7.7 (High); CWE-22 (path traversal), CWE-61 (symlink following), CWE-367 (TOCTOU). Affected `@anthropic-ai/claude-code` npm package < 2.1.129; fixed in 2.1.129. This is the latest of a recurring pattern of disclosed Claude Code sandbox-escape/bypass advisories through 2026, all on the project's own GitHub Security Advisories page (github.com/anthropics/claude-code/security/advisories): GHSA-7835-87q9-rgvv "Sandbox Escape via Git Worktree Path Confusion" (2026-06-25, High), CVE-2026-39861 "Sandbox Escape via Symlink Following" (CVSS 8.8, High — same symlink-following mechanism as the Oct 5 advisory, different code path), CVE-2026-25725 "Sandbox Escape via Persistent Configuration Injection in settings.json" (High), plus unrelated host-level issues GHSA-5p5x-5294-qhp3, GHSA-3rwf-2g6p-c2f9, GHSA-5cwg-9f6j-9jvx. Independent secondary coverage (e.g. a security newsletter's "week of sandbox escapes" roundup) frames this as a cross-vendor pattern also seen in OpenAI Codex, Cursor and Gemini CLI, not unique to Claude Code — noted here as context, not relied on as a source for any claim.
- **Technical summary:** The sandbox's filesystem confinement is enforced by path validation that happens once (at permission-check time) rather than being re-checked atomically at the moment of the write syscall. Any TOCTOU gap of this shape lets a symlink substitution redirect a benign, already-approved write to a sensitive host path (the GHSA text gives shell configuration files as the example impact). The fix (2.1.129) re-validates at write time; the underlying bug class (trust a path once, use it later) is exactly the kind of thing worth naming explicitly rather than only gesturing at "a determined attacker."
- **Why it might matter:** Lesson 09.5 teaches the sandbox as the actual enforcement boundary — "a Bash rule matches the command text... For enforcement that does not depend on the command text you need the sandbox" and "the sandbox is the boundary" — with the Limitations section only generically noting "a determined adaptive attacker may still find a path." This gives a dated, CVSS-scored, vendor-patched, primary-sourced incident in the exact product and mechanism the lesson teaches, and shows it is a recurring vulnerability *class* (TOCTOU/symlink races), not a one-off curiosity — good concrete material for "what it does NOT guarantee" / "how an attacker adapts" and for the "keep auto-update on" mitigation already implicit in the lesson's design.
