- **hosting model** — Where coding-agent inference runs and whose account and network the request uses: vendor SaaS API, cloud-hosted model on a hyperscaler, private deployment, or self-hosted open weights (lessons/module-12/lesson-01.md)
- **cost per successful task (with fixed cost)** — (marginal cost per attempt + fixed monthly cost / attempts) / pass rate, plus (1/pass rate − 1) × review cost of a failed attempt; the unit for comparing hosting options that survive the hard constraints (lessons/module-12/lesson-01.md)
- **model gateway** — The component between agent clients and model providers that holds provider credentials and centralises attribution, quotas and budgets, audit logging, routing and fallback (lessons/module-12/lesson-02.md)
- **model routing** — The gateway's choice of provider route for a request, including fallback to a secondary route on failure; every route must satisfy the same residency, feature and eval constraints (lessons/module-12/lesson-02.md)
- **token bucket** — A rate limiter whose capacity refills continuously up to a maximum; a request passes if the bucket holds enough tokens, otherwise it receives a 429 (lessons/module-12/lesson-02.md)
- **noisy neighbour** — One consumer's load exhausting a shared limit so that other consumers are throttled; fixed by placing quota boundaries where load originates (lessons/module-12/lesson-02.md)
- **chargeback / attribution coverage** — Allocating model spend to the teams that caused it; coverage is the share of spend on keys owned by a team (lessons/module-12/lesson-02.md)
- **blast radius (of a credential)** — The share of teams or systems a leaked credential can reach, k/T for a credential shared by k of T teams (lessons/module-12/lesson-03.md)
- **exposure window** — How long a leaked credential remains usable; about half its lifetime if the leak is undetected, capped by detection and revocation (lessons/module-12/lesson-03.md)
- **workload identity federation** — Exchanging a platform-issued identity token (such as a CI job's OIDC token) for a short-lived cloud or service credential, so no long-lived secret is stored (lessons/module-12/lesson-03.md)
- **managed settings** — Agent configuration deployed by the organisation that overrides user, project and local settings, used to enforce gateway URL, credentials helper, permissions, MCP allowlists and telemetry (lessons/module-12/lesson-03.md)
- **redact-before-write** — Removing secrets and personal data from prompt content before any log sink, keeping metadata and a content hash for audit (lessons/module-12/lesson-03.md)
- **append-only (WORM) audit log** — An audit trail stored so that records can be added but not modified or deleted, including by the people being audited (lessons/module-12/lesson-03.md)
- **data inventory** — A list of every copy of prompt data in a system with where it is processed and stored, how long it is kept, who can read it and which terms govern it (lessons/module-12/lesson-04.md)
- **data residency** — The requirement that data is processed and stored only in named geographies; a property of every path (fallback routes, tools, telemetry), not only the primary route (lessons/module-12/lesson-04.md)
- **inference geography vs storage geography** — Where a model processes a request versus where data is stored at rest; providers expose them as separate settings or behaviours (lessons/module-12/lesson-04.md)
- **zero data retention (ZDR)** — A provider arrangement under which request data is not persisted after processing, available only to qualifying accounts (lessons/module-12/lesson-04.md)
- **architecture decision record (ADR)** — A short, numbered, immutable record of one architecturally significant decision: context, options considered, decision, consequences and how compliance is confirmed (lessons/module-12/lesson-05.md)
- **supersession** — Replacing an accepted ADR by writing a new one that states "Supersedes: ADR-NNNN" and marking the old one "Superseded by", instead of editing it (lessons/module-12/lesson-05.md)
- **reference architecture** — The agreed description of a platform's components, flows and trust boundaries, here a C4 context and container view with a machine-readable twin checked in CI (lessons/module-12/lesson-05.md)
- **security review questionnaire** — The structured set of questions (here 30 in eight categories) that an enterprise's security, legal and architecture functions ask before approving a platform; each answer needs checkable evidence (lessons/module-12/lesson-05.md)
