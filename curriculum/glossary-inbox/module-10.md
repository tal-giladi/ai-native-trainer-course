- **Multi-agent system** — Two or more agents, each a model in a loop with its own context and tools, whose outputs feed each other through handoffs and shared state (lessons/module-10/lesson-01.md)
- **Topology (agent topology)** — The shape of a multi-agent system: single, chain, review loop, specialists, parallel or hierarchical (lessons/module-10/lesson-01.md)
- **Orchestration** — Deciding which agent runs next and with what input; done in code (a deterministic pipeline) or by a lead model (lessons/module-10/lesson-01.md)
- **Orchestrator-workers** — A topology in which a lead (model or code) splits work, delegates parts to worker agents and combines their results (lessons/module-10/lesson-01.md)
- **Review loop (evaluator-optimizer)** — A worker produces a result, a reviewer approves or requests changes, and the worker revises until approval or a stop condition (lessons/module-10/lesson-01.md)
- **Voting (parallel sampling)** — Running the same task several times and letting a check or a majority pick one result; extra compute rather than collaboration (lessons/module-10/lesson-01.md)
- **Implicit decision** — A choice (a name, a signature, a default) that an agent makes silently while acting; parallel agents that cannot see each other make it inconsistently (lessons/module-10/lesson-01.md)
- **Handoff contract** — The written agreement on one edge of a pipeline: what is passed, in what shape, how code validates it, and what happens when it is invalid (lessons/module-10/lesson-02.md)
- **Lease (file ownership)** — A rule that only one agent may write a file at a time, usually derived from the files a plan declares it will touch (lessons/module-10/lesson-02.md)
- **Merge policy** — How the results of parallel writers are combined: naive last-writer-wins, detect conflicts, rerun the loser on top, or serialize overlapping tasks (lessons/module-10/lesson-02.md)
- **Precedence order** — A fixed ranking of sources (task criteria, project rules, role preferences) that agents' findings must cite, used to settle disagreements between agents (lessons/module-10/lesson-02.md)
- **Critical path** — The longest sequence of dependent stages in a pipeline; it sets wall-clock latency, since parallel stages cost only their slowest branch (lessons/module-10/lesson-03.md)
- **Reviewer equation** — One review round changes success by (1 - p) r p_fix - p f d: rescued wrong results minus correct results broken by rework after false alarms (lessons/module-10/lesson-03.md)
- **Oscillation stop** — An orchestrator rule that escalates to a person when the planner keeps its plan and the reviewer repeats the same finding (lessons/module-10/lesson-03.md)
- **Agent trace** — One record per task with one span per agent call (role, round, timing, cost, tokens, verdict, files) and a stop reason, used to find where a failure originated (lessons/module-10/lesson-03.md)
- **MAST** — A taxonomy of 14 multi-agent failure modes in three categories: system design issues, inter-agent misalignment and task verification (lessons/module-10/lesson-03.md)
- **Compute-matched baseline** — A single agent allowed the same kinds of work as a multi-agent arm (plan, test, re-check), so a comparison isolates the effect of having several agents (lessons/module-10/lesson-04.md)
