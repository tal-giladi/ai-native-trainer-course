# Pain / problem map — worksheet

For [01.4](../../../lessons/module-01/lesson-04.md). One row per **pain**, not per interview. A pain enters the map only with at least one past, specific event behind it; opinions go in the parking lot at the bottom.

```markdown
# Pain map — <wedge short name> — after <n> interviews — <yyyy-mm-dd>

| Id | Pain (in their words) | Heard in | Verbatim quote (anonymized) | Last event (when, what) | Frequency | Size (engineer-hours / month, low–high) or flow effect | Current workaround | User | Champion | Buyer | Blocker | AI-related? |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| P1 | | I01, I03 | "" | | | | | | | | | yes / no / worse with AI |

## Problem statements (one per pain heard in ≥ 2 interviews)
- P1: <audience> loses <size> because <mechanism>; today they <workaround>; <buyer> would care because <…>.

## Parking lot (opinions, wishes, hype — not evidence)
- 

## Verdict
Keep / change / kill the wedge — and the evidence line that decided it.
```

Column notes:

- **Heard in** counts independent interviews. Two people from the same team telling the same story is one data point.
- **Size**: engineer-hours (effort) and calendar delay (flow) are different units; never multiply one into the other (01.2).
- **AI-related?** Many of the best pains are not about AI at all (a review bottleneck, slow onboarding). Mark whether agents could help, would not matter, or would make it worse.
